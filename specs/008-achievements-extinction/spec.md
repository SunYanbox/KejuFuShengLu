# Feature Specification: 成就与绝嗣结局（逻辑轨 ⑧）

**Feature Branch**: `008-achievements-extinction`

**Created**: 2026-10-18

**Status**: Draft（Q1~Q3 已于 2026-10-18 裁决并回填）

**Input**: User description: "$speckit-specify 上一次做了007相关功能，下一步应该做什么"

## 范围来源（本特性的授权与边界）

- **规格书 §16.1 逻辑轨顺序**：① slnx + Core → ② Rules 月结算引擎 → ③ 开局资产与官吏体系 →
  ④ 存档体系 → ⑤ 科举周期 → ⑥ 贿赂全链路 → ⑦ 婚姻与生育 / 疾病 / 寿命 / 家主继任 / 收养 →
  **⑧ 成就与绝嗣结局** → ⑨ 难度装配与打磨。007（逻辑轨 ⑦）已交付，故下一条即本特性。
- **§16.2 旧编号对照**：旧「⑪ 成就 / 绝嗣结局」= 新逻辑轨 **⑧**；本特性是**纯逻辑轨**特性，
  MUST 可完全脱离界面被验收（§16.1 约束 3），MUST NOT 阻塞也不被 U 轨（U1/U2/U3/U4）阻塞。
- **需求真源**：§14.1 成就 68 条 + §15 结束条件 + §14「成就为全局持久化（独立于存档的
  achievements.json，记录来源存档 UUID）」+ §16.1 的「必测单测清单」第 9 条「绝嗣判定（外嫁不计）」。
- **本特性 MUST NOT 自造平衡数值**（§17 末句）：所有判据只引用既有规则产物与既有派生谓词；
  新出现的口径一律登记为 §17 裁决（见 Assumptions 与 FR-048 的回写清单）。

## Clarifications

### Session 2026-10-18（Q1~Q3 已裁决）

**Q1：「触发源尚未交付」的 6 条成就（`商海浮沉` + 调试秘辛 5 条）如何处置？**
→ **裁决：交付全部 68 条定义 + 计数接缝 + 待接线清单（选项 A）。**
§14.1「调试秘辛系列」的 5 条以「唤醒调试控制台」为触发源，而调试控制台属**界面轨 U4**（§16.1）；
`商海浮沉` 以「经商亏损事件（损失本金 10~30%）」为触发源，007 已把「每年 10% 概率亏损事件」
明确排除在 ⑦ 之外，规格书亦**未定义**该事件的概率与幅度。故 008 为这 6 条交付**成就定义、判据、
可由外部上报的累计接缝与待接线清单（FR-043）**，MUST NOT 实现调试控制台（FR-041）、
MUST NOT 自造亏损事件规则（FR-042）。理由：既不改动 U4 的分工，也不让 §14.1 在本阶段留下缺口。

**Q2：成就判定的时点、幂等与「回退语义」？**
→ **裁决：月末统一判定 + 动作型事实即时判定；解锁不可撤销（选项 A）。**
① 每回合**结算完成后、写盘之前**统一判定一次，消费当月报告（`SettlementResult` 六类快照）与
期末状态；② FR-009 列出的动作型事实（新局创建、资产买卖、贷款与清偿、托媒/提亲应答/买功名婚姻、
收养、行贿提交、科举询问应答、调试唤醒上报）在动作成功后**立即**判定一次；
③ 全局记录**只增不减**，读档或回退到解锁之前的月份 MUST NOT 撤销已解锁项。
理由：瞬时事实（同月 5 人在职、死刑当场执行、连坐名单、被释放）在月末前可能已消失，
只靠月末扫状态必然漏判；而「偶发动作点判定」会让同一事实出现多个出处且不可复现。
解锁不可撤销则使成就成为**跨档的既成历史**，与 §14「全局持久化、记录来源存档 UUID」一致。

**Q3：编年史与成就累计事实的持久化形状？**
→ **裁决：随档新增累计器与结束状态，`SaveFileFormat.Version` 4 → 5，旧档按既有版本闸门拒绝读取（选项 A）。**
§15 要求结局画面给出「存续年数、传承代数、**峰值资产**、最高功名、进士总数、**平均寿命**、
完整族谱」；其中「峰值资产」与「平均寿命」**无法**从既有持久数据重算（账本只记条目、不含资产
市值序列；成员死亡只当月落 `DeathFact(PersonId, DeathCause)`，**不存享年**），故必须新增持久累计器
（FR-013 的 ①~⑧）。处置与 007 对 `Version` 3 → 4 一致：**不做就地迁移**，旧档以既有版本闸门拒绝读入。
理由：把累计量放进全局 `achievements.json` 会造成「读档回退后计数超前、状态落后」的不一致
（累计量必须随档一起回退），而「全部靠重算」会让峰值资产与平均寿命永久缺席。

### Session 2026-10-18（次级口径复核 A~D + 三均值细化，已裁决）

起草时标注的 4 条 ⚠ 次级口径经用户逐条复核，结论如下（均已落入 Assumptions 5~7、12 与成就判据总表）：

- **A 存续年数门槛 → 逐字从严**：`百年世家` 取 **> 100**（当前年 102）、`千秋万代` 取 **> 300**
  （当前年 302）、`绝处逢生` 取 **≥ 100**（当前年 101）。依据：§14.1:611/:612 写「超过」，
  :570 写「连续存活 100 年」（无「超过」）——不统一取整，以免擅自放宽规格书门槛。
- **B 传承代数 → 最大 `Generation` + 1**：辈分是 **0 基准**（§4.4:115 与 `Family.cs:138` 写死
  「开局成员辈分 MUST 为 0」），故编年史记「第 N 代」时取最大值 + 1，与 §14.1:564
  「家族传承至第五代」自洽 ⇒ `五世其昌` = `Generation >= 4`。
  **本项同时修正了起草稿的一处事实错误**（原稿误记「开基家主辈分为 1」，并把 `五世其昌` 写成 `>= 5`）。
- **C 平均寿命 → 已故成员「享年」分布的三均值（Tukey trimean）**：`TM = (Q1 + 2·Q2 + Q3) / 4`，
  Q1/Q2/Q3 按 **Tukey hinges** 取（中位分两半、各半取中位；**奇数样本时中位计入两半**），
  `decimal` 运算、保留 **3 位小数**；分子为每个已故成员死亡当月的 `Person.AgeAt`（含夭折、
  连坐处死、饥馑/患病死亡与外嫁归档成员）；样本不足（n ≤ 3）也照公式算、`n = 0` 取 0。
  不取「天命寿数（`Person.Lifespan`）均值」（那是出生时 roll 出的分配值，长期稳定在 ~61 岁、
  对玩家无信息量），也不排除稚龄死者（规格书未定义阈值，属自造）；不取算术平均
  （**本项修正了我第一轮把「三均值」误读为算术平均的理解**）。
  ⇒ 累计器形状随之变化：FR-013 ③ 必须是**逐个追加的享年完整序列**（只存「和 + 个数」无法反推分位点）；
  ⇒ 金色算例与判别例见 Assumptions 7（测试 MUST 逐行钉死）。
  **注（口径澄清）**：提问时选项 A 的标签写作「弃中位」，但 Tukey hinges 的标准定义（Tukey 1977 与
  R `fivenum`）是**奇数样本时中位计入两半**，且同轮 Q2 的裁决文本亦写「中位参与两半」；
  本规格书按**标准定义取「计入」**，并用 Assumptions 7 的 `[10, 20, 30, 40, 100]` 判别例
  （计入 ⇒ 30.000 / 弃中位 ⇒ 36.250）把它钉死，MUST NOT 实现成排他口径。
- **D 榜下捉婿 → 历史上出现过 `Kind == ImperialProposal` 的提议即解锁（含被拒）**：
  007 已把捉婿候选钉死为「上月新科一甲（`ImperialPlacement.First`）、及第次月、每科一次」
  （specs/007-family-lifecycle/contracts/marriage-birth.md:82、该特性 FR-019），
  故候选范围无需再收窄；判据只读 `Kind`。口径与 §14.1:600「触发……被富商提亲**事件**」一致
  （事件型成就：提议产出即成立，不看玩家是否接受）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 成就自动解锁与全局持久化（Priority: P1）

玩家在任意难度下推演家族：家族首次出现举人/进士、资产越过万贯、有人行贿成功、有人被处死……
每达成一条，系统自动判定并解锁对应成就；解锁记录写入**独立于存档**的 `achievements.json`，
记下该成就**各难度各自的最早完成日期**与来源存档 UUID；之后新建一个简单难度的存档，
成就列表里该成就已带「简单/普通/困难」等难度徽章。

**Why this priority**：这是 §14 与 §14.1 的正面需求，也是 006/007 已预留派生谓词
（`PunishmentQueries.FamilyCumulativeBribes`、`WasBribeFreeAtImperialPass`、`WasExecutedByState`、
`IsLevelCapReached`；`LifecycleSnapshot` 的六类当月事实）的**唯一消费者**——不交付它，
这些预留就永远没有出口，而「成就」这一整块需求表现为零。

**Independent Test**：注入固定种子的测试驱动器，逐月推进并在任意一点断言
`AchievementState.Unlocked` 与 `achievements.json` 的内容即可，**不需要任何界面**；
也可用「构造一个已满足条件的 `GameState` → 调一次判定」直接验证单条成就。

**Acceptance Scenarios**：

1. **Given** 一份 001 年 1 月新档、全局 `achievements.json` 不存在，**When** 新局创建完成，
   **Then** `ACH-001 开基立业` 被标记为已完成并进入待落盘队列（来源 UUID = `GameState.Id`，
   难度 = 本档难度，日期 = 当前游戏年月），且**不**因此产生任何界面依赖。
2. **Given** 家族尚无举人，**When** 某月结算中一名成员中解试（`ExamOutcomeLine.Passed == true`、
   并因此得到举人功名），**Then** 该月判定后 `ACH-002 首个举人` 与 `ACH-013 杏林初茂` 的计数同步推进；
   若这是第 1 名举人则 `ACH-002` 解锁；累计到第 3 名时 `ACH-013` 解锁。
3. **Given** 家族已解锁「投石问路」并已在简单难度记下 001 年 5 月，**When** 在普通难度新建档并
   首次行贿成功，**Then** `achievements.json` 中该成就同时保留「简单 001-05」与「普通 00X-YY」两条
   难度标记，**MUST NOT** 覆盖或迁移简单难度那条。
4. **Given** 一条已解锁记录，**When** 同一成就、同一难度、更晚的日期再次达成，
   **Then** 全局文件中该难度下的日期**保持不变**（只保留最早日期）。
5. **Given** 全局文件与存档目录都可写，**When** 一个回合作出 2 条解锁，**Then** 两条在一次
   落盘内一起写入（原子替换），不存在「写了一半」的文件。

### User Story 2 - 瞬时与累计事实的确定性记账（Priority: P1）

家族同时有 5 人在职为官、同一月有 3 人服刑、某人政绩满值、某人在 50 岁后第 6 次省试落榜并
被授特奏名——这些**瞬时事实**（只在本月成立）与**累计事实**（累计行贿成功次数、累计出生人数、
曾经的贷款、峰值资产）在**同一套确定性口径**下被记账与判定：同一随机种子的两次推演必须得到
完全相同的解锁结果与完全相同的解锁日期。

**Why this priority**：成就若靠「月末扫一遍当前状态」实现，瞬时事实（同月 5 人在职、连坐、
被释放）会在月末前消失；若靠「各动作点自己判定」，同一事实会有 N 个出处且不可复现。
必须先定死「事实从哪来、累计量存在哪、何时判定」这一层，US1 才可能正确。

**Independent Test**：同一 `GameState`（同种子）跑两次 N 个月的推演，断言
`AchievementState` 的计数器与解锁集合逐字段相同；再用人工构造的报告（`SettlementResult`）
断言每一条瞬时判据都能从报告单独触发。

**Acceptance Scenarios**：

1. **Given** 州里当月有 5 名成员在职，**When** 该月判定执行，**Then** `ACH-025 袍笏登场` 解锁；
   **When** 次月只剩 4 人在职，**Then** 该成就**不会**被撤销，也不会重复写入第二条记录。
2. **Given** 某成员本月被判处死（困难殿试行贿被抓），**When** 该月判定执行，
   **Then** `ACH-055 身首异处` 解锁，且判据**只**取自该月报告的「被抓的殿试行贿事实 + 该难度该级别的
   惩罚格为立即执行」，**MUST NOT** 用「成员已亡」这一更宽的谓词冒充。
3. **Given** 家族从未借过钱，**When** 某月贷款**本金超过 100 贯**（**严格 `>`**，口径见「成就判据总表」
   ACH-042 与 `Assumptions 4`），**Then** `ACH-042 债台高筑` 解锁；
   **When** 后续月份本金与欠息全部结清（`Loan.IsSettled`），**Then** `ACH-043 无债一身轻` 解锁；
   **MUST NOT** 出现「先结清后举债」也能解锁「无债一身轻」的次序倒置。
4. **Given** 累计出生人数在若干年内达到 50（含夭折者），**When** 达到的那一月判定执行，
   **Then** `ACH-033 百子千孙` 解锁；判定**MUST NOT** 依赖「夭折者是否还在册」。
5. **Given** 两名成员的学业均为 85，**When** 其中一人省试落榜、另一人中第，**Then**
   `ACH-031 名落孙山` **只**因落榜者而解锁。

### User Story 3 - 绝嗣判定与编年史结局快照（Priority: P1）

家族最后一名在册成员死去（外嫁归档者不算在册），本回合结算完成后系统判定**绝嗣**：
记录结局发生的年月，冻结一份**编年史快照**（存续年数、传承代数、峰值资产、最高功名、进士总数、
平均寿命、族谱数据），并解锁 `ACH-044 烟消云散`（地狱难度另加 `ACH-048 大梦一场`）。

**Why this priority**：§15「唯一终点 = 家族绝嗣」是整个游戏的**终止条件**，也是 §16.1
「⑧ 成就与绝嗣结局」这一编号里的另一半；没有它，推演就没有终点，成就业也缺一条主锚。

**Independent Test**：构造一份只剩 1 名在册成员、且该成员寿命必在本月耗尽的存档，推进一回合，
断言 `EndingState.IsEnded`、结局年月、编年史七个字段的具体取值；再用「只剩外嫁归档者」的存档
断言**不**判绝嗣。

**Acceptance Scenarios**：

1. **Given** 家族在册成员 2 人、当月两人同时死亡，**When** 结算完成并判定，
   **Then** `EndingState.IsEnded` 为真、`EndedOn` = 该月，且 `烟消云散` 在该月解锁。
2. **Given** 家族全部成员「已亡」或「外嫁归档」，但族谱中仍有人在册服刑或待阙，
   **When** 判定执行，**Then** **不**判绝嗣（§15 口径：在册存活 + 服刑 + 待阙 ≠ 0）。
3. **Given** 家族只剩一名已外嫁归档的女儿（无任何在册成员），**When** 判定执行，
   **Then** 判绝嗣（外嫁**不计**）。
4. **Given** 家族存续年数达到 101（= 当前年 102）且未绝嗣，**When** 该年首月判定执行，
   **Then** `百年世家` 解锁；**Given** 家族在存续年数达到 101 之前绝嗣，**Then** `百年世家` **不**解锁；
   **Given** 存续年数恰为 100，**Then** `百年世家` **不**解锁但地狱难度下 `绝处逢生` **会**解锁
   （两条门槛口径不同，见 Assumptions 5）。
5. **Given** 一份已绝嗣的存档，**When** 结局判定执行，**Then** 编年史的七个字段同时可用：
   存续年数（当前年 − 1）、传承代数（最大 `Generation` + 1）、峰值资产（历史月末最大总资产）、
   最高功名（族谱历史最高）、进士总数（族谱历史累计）、平均寿命（全部已故成员**享年分布的三均值**，含夭折）、
   完整族谱（全量成员数据，绘制属界面轨 U2）。

### User Story 4 - 结局后的状态机与存档语义（Priority: P2）

结局一旦触发，该存档进入**已结束**状态：不再允许推进回合（不会出现第二次绝嗣或第二次结局），
但存档仍可正常写盘与读回（读回后仍是「已结束」），备份仍可回退到绝嗣之前的月份继续玩；
全局成就记录**不受**读档或回退影响。

**Why this priority**：§15 说结局画面提供「读档 / 回主菜单」，而界面属 U 轨；逻辑轨必须先给出
**可被 U 轨直接消费的结束状态**与**不会自相矛盾的状态机**，否则 U1 会在结束态上继续推进月份。

**Independent Test**：在已结束的存档上调用推进一回合，断言以明确的异常拒绝（或等价的可断言结果）；
再把该档写盘、读回，断言结束状态与编年史快照逐字段一致；最后用备份覆盖主文件后推进，断言可以继续玩。

**Acceptance Scenarios**：

1. **Given** 一份已结束的存档，**When** 调用推进一回合，**Then** 以
   `InvalidOperationException` 拒绝且**不**改动任何状态（不消费随机、不落账本条目、不写盘）。
2. **Given** 一份已结束的存档，**When** 写盘后读回，**Then** 结束标记、结局年月与编年史快照
   逐字段一致，且全局成就记录**不**因此产生新的解锁。
3. **Given** 一份已结束的存档与它 3 回合前的备份，**When** 把备份复制回主文件并读回，
   **Then** 该档可继续推进，且此前已解锁的成就**保持**解锁。
4. **Given** 存档目录不可写，**When** 该回合产生了 2 条新解锁，**Then** 回合推进本身
   MUST NOT 被成就落盘失败阻断（失败以可诊断的方式上报，待落盘队列保留在档内，下次重试）。

### User Story 5 - 「触发源未交付」成就的接线与待办登记（Priority: P3）

调试秘辛 5 条（唤醒调试控制台 1/10/100/1000/10000 次）与「商海浮沉」（经商亏损事件）的
**触发源**分别属界面轨 U4 与尚未排期的随机事件表。本特性交付它们的**成就定义与计数接缝**
（一个可被外部上报的累计入口 + 待接线清单），MUST NOT 自建调试控制台、MUST NOT 自造亏损事件的
概率与幅度。

**Why this priority**：6/68 条成就的触发源不在本特性范围内；若为此自造规则，会直接违反
§17「禁止自创影响平衡的核心数值」，并把 U4 的实现方式提前钉死。

**Independent Test**：以测试驱动器**直接上报**唤醒计数 10 次，断言 `窥探虚实` 解锁；
不触碰任何界面代码。

**Acceptance Scenarios**：

1. **Given** 唤醒计数为 0，**When** 上报 1 次唤醒，**Then** `天机泄露` 解锁；再上报到 10 次，
   **Then** `窥探虚实` 解锁；计数**累计并随档持久化**（读回后不归零）。
2. **Given** 本特性完成，**When** 审查交付物，**Then** 存在一份「待接线成就清单」，逐条写清
   待接线项、所属后续阶段（U4 / ⑨）与需要外部提供的上报内容。
3. **Given** 一次上报，**When** 判定执行，**Then** 该上报**不**消费随机、**不**落账本条目、
   **不**改变家族经济与成员状态。

### Edge Cases

1. **同月同时绝嗣与解锁**：最后一名成员死亡导致绝嗣的同一月，另一条成就（如 `路有冻骨`）也成立 ⇒
   两者必须同时解锁（绝嗣判定**不**短路其他成就判定；顺序固定为「先成就、后绝嗣」，或「先绝嗣、
   后成就」但必须**明写**并由测试钉死，MUST NOT 依赖实现的偶然次序）。
2. **同月多条解锁 + 写盘失败**：待落盘队列 MUST 完整保留（含解锁年月与来源 UUID），
   下次成功后**一次性**写入，日期取原解锁年月而非重试当时的年月。
3. **难度为待生效难度（`PendingDifficulty` 非空）**：成就难度标记 MUST 取**当前生效难度**
   （`GameState.Difficulty`），MUST NOT 取 `PendingDifficulty`；切换生效后再次达成按新难度另记一条。
4. **同一成就同一月被两条路径同时触发**（如两笔行贿使计数同时跨过阈值）⇒ 只落**一条**记录。
5. **存续年数的边界**：新建档固定 1 年 1 月，故存续年数 = 当前年 − 1；门槛**按规格书逐字分档**——
   `百年世家`（> 100 ⇒ 当前年 102）与 `千秋万代`（> 300 ⇒ 当前年 302）为**严格大于**，
   `绝处逢生`（≥ 100 ⇒ 当前年 101）为**大于等于**；三条各自的解锁点由测试逐点钉死。
6. **第五代判定与「收养的旁系成员辈分」**：收养的辈分 = 家主辈分 + 1（§4.4:119）⇒ 收养多了也可能
   推进「最大辈分」。本特性取「最大 `Person.Generation` + 1」为传承代数口径，
   并据此把 `五世其昌` 定为 `Generation >= 4`（0 基准），MUST NOT 另立第二套代数定义。
7. **外嫁成员的成就贡献**：`红颜薄命`（分娩死）与 `殃及池鱼`（跨族追及）**必须**包含已外嫁归档者；
   而 `人丁兴旺`、`三代同堂`、`五世其昌`、`袍笏登场` **必须**只数在册成员的存活口径。
8. **「清白传家」与改名/读档**：谓词只由功名变迁史与三个行贿计数派生，故读档后结论不变；
   MUST NOT 把它落盘成第二个真源。
9. **资产阈值与月末采样**：若玩家买入 100 亩后在同月内卖出，则月末采样看不到 100 亩 ⇒
   买入动作成功后 MUST 触发一次判定（见 FR-009），使「阡陌交通」不因同月卖出而漏判。
10. **全局文件损坏或不可解析**：MUST NOT 崩溃、MUST NOT 删除玩家既有存档；按「隔离损坏文件 +
    从空表开始」处理，流程与后述假设一致，并把损坏路径上报。
11. **同一 UUID 出现在两个文件名下**（004 已定义的冲突族）：成就记录以 UUID 为来源标识，
    MUST NOT 因档名变化而产生第二条来源记录（同一 UUID + 同一难度 + 同一成就仍是同一条）。
12. **零在册但家主之位空悬**：`LifecycleSnapshot.HeadBecameVacant` 是「无在册男性」，
    **不等于**绝嗣（007 已明写）；本特性 MUST NOT 用家主是否空悬代替绝嗣判据。
13. **调试唤醒计数上报超过 10000**：计数 MUST NOT 溢出、MUST NOT 清零；更高档位不再有成就。
14. **一次上报在已结束的存档上**：MUST NOT 触发任何新解锁（结束态冻结成就判定）。
15. **同一成就的定义在未来扩展**（如新增难度）：既有记录 MUST 保持可读，
    全局文件 MUST 带自己的版本号以便向后兼容判断。
16. **「平均寿命」的样本量与边界**：三均值在 n = 1/2/3 时**照公式算**（不设特例、不显示「样本不足」，
    用户裁决），`n = 0`（尚未有人死亡）取 **0.000** 且 MUST NOT 抛异常；结局快照必然 n ≥ 1
    （绝嗣 ⇒ 至少 1 人死亡）。小数位固定 3 位（`MidpointRounding.AwayFromZero`，
    内部 `decimal` 不提前截断）。金色算例与**判别例**见 Assumptions 7（测试 MUST 逐行钉死）。

## Requirements *(mandatory)*

### A. 覆盖与复用（真源纪律）

- **FR-001**：本特性 MUST 为 §14.1 的**全部 68 条**成就各定义一条稳定标识（`ACH-001`~`ACH-068`，
  与 §14.1 的书写顺序一致），并给出**可断言**的判据；判据总表见下节「成就判据总表」。
- **FR-002**：本特性 MUST 交付 §15 的绝嗣判定与编年史快照（见 US3），
  判定口径 MUST 为「在册成员数 = 0」，在册口径 MUST 复用既有派生入口
  （`KFL.Core/Entities/Family.cs` 的 `RegisteredMembers`；其定义「非已亡且非外嫁」与 §15 一致），
  MUST NOT 另立第二套「在册」定义。
- **FR-003**：**派生谓词 MUST NOT 落盘**：`WasBribeFreeAtImperialPass`、`WasExecutedByState`、
  `FamilyCumulativeBribes`（`src/KFL.Rules/Punishment/PunishmentQueries.cs`）、
  资产阈值（`src/KFL.Rules/Economy/TotalAssetsCalculator.cs` 的 `Of`）、
  田地/铺面阈值（`src/KFL.Core/Entities/Holdings.cs` 的 `FarmlandMu` / `Shops`）、
  「在职人数」（`Person.Rank`）、「政绩」（`Person.Merit`）等**一律在判定时从状态重算**，
  MUST NOT 复制成持久字段。唯一例外是**不可重算**的累计量（见 FR-012）。
- **FR-004**：本特性 MUST NOT 新增、修改任何影响平衡的数值（概率、金额、阈值、月份数）；
  判据里出现的阈值全部来自 §14.1 原文与既有配置单点。
- **FR-005**：短名 MUST 固定为 `achievements-extinction`，特性目录 MUST 为
  `specs/008-achievements-extinction`；本特性 MUST NOT 引入新的技术栈、框架或第三方依赖
  （章程「技术栈约束」）。

### B. 判定时点、幂等与可复现

- **FR-006**：成就判定 MUST 只有一个实现入口（`KFL.Rules` 内的成就判定器），
  MUST NOT 在各业务点各写一套判定；业务点只负责**触发**与**上报事实**。
- **FR-007**：判定 MUST 至少在一回合的**结算完成之后、写盘之前**执行一次
  （对齐 `src/KFL.Rules/Save/TurnRunner.cs` 的 `Advance` 编排：结算 → 判定 → 覆盖写档 → 备份），
  使该回合的全部当月事实（`SettlementResult` 的 `Punishment` / `Career` / `ExamSeason` /
  `Lifecycle` / `FamineBefore` / `FamineAfter` 六类快照）都可被消费。
- **FR-008**：判定 MUST 同时消费**状态面**（家族、资产、官职、田地铺面的当前值），
  使 `人丁兴旺`、`三代同堂`、`五世其昌`、`寿比南山`、`家资万贯`、`富甲一方`、`阡陌交通`、
  `良田万顷`、`旺铺之主`、`债台高筑`、`政通人和`、`位极人臣` 这类**期末状态**成立。
- **FR-009**：**动作型事实 MUST 在动作成功后立即触发一次判定**（不等月末），
  至少覆盖以下公开入口：新局创建、资产购入与售出、贷款发生与提前清偿、
  托媒/提亲应答/买功名婚姻、收养、行贿提交、科举询问应答、调试唤醒上报。
  理由与边界见 Edge Cases 9；此清单 MUST 由契约登记，新增动作入口时必须同步。
- **FR-010**：解锁是**单向**的：一旦某成就某难度被记为已完成，MUST NOT 被任何后续状态、
  读档或回退撤销（见 US4 AS3）。
- **FR-011**：判定 MUST 幂等：同一状态重复判定、或同月两条路径同时命中同一成就，
  MUST 只产生一条记录（同成就 + 同难度 + 同日期视为同一条）。
- **FR-012**：判定 MUST NOT 读取系统墙钟、MUST NOT 读取系统区域设置、MUST NOT 消费随机
  （G-07 同类约束：`KFL.Rules` 不得直接触达文件系统与时钟）；全局文件的读写 MUST 经
  注入的接缝（与既有 `ISaveService` 同款形状）完成。**同种子两次推演 MUST 产生逐字段相同的
  解锁集合与解锁日期。**

### C. 不可重算的累计事实（持久化最小集）

- **FR-013**：随档持久化的累计量 MUST 只包含**无法从既有持久数据重算**的项，且逐项可测：
  ① 累计行贿**成功**次数（`Caught == false` 的事实计数——既有成员计数器计的是**尝试**次数，
  不能替代）；② 累计出生人数（含夭折）；③ **已故成员的享年序列**（逐个追加死亡当月的
  `Person.AgeAt`，含夭折/连坐/外嫁；序列长度即历史死亡人数）——**MUST 为完整序列而非「和 + 个数」**：
  编年史「平均寿命」按**三均值**口径需要 Q1/Q2/Q3 三个分位点，仅靠均值无法反推（见 FR-028 ⑥ 与
  Assumptions 7 的算例）；
  ④ 月末总资产的**历史峰值**；⑤ 是否**曾经**产生过贷款（「无债一身轻」需要次序，见 US2 AS3）；
  ⑥ 调试控制台唤醒次数（外部上报）；⑦ 各成就的已完成集合与完成年月；
  ⑧ 待落盘的解锁队列（含解锁年月与来源 UUID）。
- **FR-014**：累计量的更新时点 MUST 与其事实来源同月同步（当月报告的六类快照 / 资产状态 / 上报），
  MUST NOT 事后回填、MUST NOT 在判定之外的地方更新。
- **FR-015**：累计量 MUST 随存档落盘和读回（FR-013 各项逐字段一致），
  其形状变更 MUST 按 AGENTS.md「跨特性形状变更的回写义务」登记回写范围。
- **FR-016**：**贷款次序**：`债台高筑` 取「历史任一时点本金 > 100 贯」；
  `无债一身轻` 取「曾经产生过贷款 ∧ 其后 `Loan.IsSettled` 为真」；
  两者 MUST 各自独立可测，不得由同一计数器派生。

### D. 全局成就文件（§14 的「独立于存档的 achievements.json」）

- **FR-017**：全局成就文件 MUST 名为 `achievements.json`，落在**当前存档根目录**下
  （即 `ISaveService.RootDirectory`，默认 `AppContext.BaseDirectory/saves`），
  与存档文件同级；格式恒为 JSON（**不**随存档格式设置变化）。
- **FR-018**：每条记录 MUST 至少含：成就标识、难度、**该难度下最早完成的游戏年月**、来源存档 UUID；
  当同样的（成就 + 难度）再次达成而日期更晚时 MUST 保留原日期。
- **FR-019**：文件 MUST 含自己的**版本号**，并以「未知字段可忽略、缺失字段取默认」的方式向后兼容
  （Edge Case 15）。
- **FR-020**：为支撑 `四民皆历`（四个不同出身的存档中各达成过「绝嗣」或「百年世家」），
  文件 MUST 另有「出身达成」段：记录 `出身 + 达成类别（绝嗣 / 百年世家）+ 游戏年月 + 来源 UUID`；
  `四民皆历` 的判据 MUST 只读该段（农/工/商/士 四者齐备 ⇒ 解锁），MUST NOT 从存档文件反推。
- **FR-021**：写入 MUST 为原子替换（临时文件 → 刷盘 → 同卷改名；与既有
  `src/KFL.Infrastructure/Save/AtomicFileWriter.cs` 同款语义），使文件任何时刻要么是完整的旧内容、
  要么是完整的新内容。
- **FR-022**：全局文件 MUST NOT 参与存档一致性校验，MUST NOT 阻塞存档读写：
  存档的可用性 MUST NOT 取决于全局文件是否存在、是否可解析。
- **FR-023**：全局文件不可解析 / 损坏时，MUST 隔离损坏文件（改名保留）并以空表继续，
  MUST NOT 崩溃、MUST NOT 静默删除；失败与隔离路径 MUST 可诊断（返回给调用方）。
- **FR-024**：全局写入失败 MUST NOT 阻断回合推进与存档（US4 AS4）：
  待落盘队列保留在档内，下一次判定时重试；重试写入 MUST 使用**原解锁年月**。
- **FR-025**：成就记录的来源标识 MUST 与存档标识（`GameState.Id`）一致，
  MUST NOT 用档名代替（改名、格式切换、复制文件都不得改变来源标识）。

### E. 绝嗣与结局

- **FR-026**：绝嗣判定 MUST 在每回合结算完成之后执行，判据 MUST 为「在册成员数 = 0」
  （外嫁归档者不计；服刑、待阙、患病、致仕者**算**在册）。
- **FR-027**：绝嗣一经判定 MUST 被持久化（结束标记 + 结局年月），
  且 MUST NOT 被同一存档的后续推进重复触发。
- **FR-028**：结局 MUST 冻结一份**编年史快照**，含 §15 的七项：存续年数、传承代数、峰值资产、
  最高功名、进士总数、平均寿命、族谱（数据面）。口径 MUST 固定为：
  ① 存续年数 = 当前年 − 1（开局固定 1 年 1 月，见 `src/KFL.Rules/Start/NewGameSetup.cs` 的
  `StartOfGame`）；② 传承代数 = 族谱中出现过的**最大 `Person.Generation` + 1**（= 第 N 代；
  辈分为 0 基准，见规格书 §4.4:115）；③ 峰值资产 = 历史**月末**总资产的极大值
  （口径 `TotalAssetsCalculator.Of`：现金 + 储蓄 + 田宅铺市值 − 贷款）；
  ④ 最高功名 = 族谱历史**全量成员**的 `Person.CurrentDegree` 的最高 `DegreeLevel`（含已亡与外嫁归档者；
  空族谱取 `DegreeLevel.BaiShen`——既有 `DegreeLevel` 枚举的零值（**不存在** `DegreeLevel.None`，见 `plan.md` E-13））；
  ⑤ 进士总数 = 族谱历史累计进士人数（按**人**计，不按次）；
  ⑥ 平均寿命 = 已故成员**享年分布的三均值**（Tukey trimean：
  `TM = (Q1 + 2·Q2 + Q3) / 4`，Q1/Q2/Q3 为享年序列的下四分位 / 中位 / 上四分位，
  按 **Tukey hinges** 取：**中位把样本分两半、各半取中位；奇数个样本时中位计入两半**
  （= R `fivenum` 口径）；`decimal` 运算、**保留 3 位小数**、`n = 0` 取 0 且不抛异常；
  享年 = 死亡当月的 `Person.AgeAt`，**含**夭折、连坐处死、饥馑/患病死亡与外嫁归档成员；
  在死亡当月追加进享年序列，不新增「死亡时间」字段。算例与边界见 Assumptions 7）；
  ⑦ 族谱 = 全量成员（既有 `Family.Members` 含归档，绘制属 U2）。
- **FR-029**：已结束的存档 MUST 拒绝继续推进回合：以明确的异常表达，且拒绝路径
  MUST NOT 改变任何状态（不消费随机、不落账本条目、不写盘）。
- **FR-030**：已结束的存档 MUST 仍可写盘、读回、改名与备份；读回后结束状态与编年史快照
  MUST 逐字段一致。
- **FR-031**：§15 的结局画面（读档 / 回主菜单）与编年史**呈现**属界面轨（U1/U2），
  本特性 MUST NOT 实现界面；逻辑轨 MUST 只提供数据面与状态机。
- **FR-032**：绝嗣当月 MUST 与成就判定在**同一次编排**内完成，且两者的先后次序 MUST 被明写并由
  测试钉死（Edge Case 1），使「绝嗣当月成立的其它成就」不被漏判。

## Key Entities

- **成就定义（静态）**：稳定标识（`ACH-001`~`ACH-068`）、系列、名称、判据标识、判定所需的
  事实种类（状态面 / 当月报告 / 累计量 / 全局段）。定义 MUST 是只读的静态表，
  MUST NOT 携带可变状态。
- **成就累计器（随档持久化）**：FR-013 的 ①~⑧。它是**唯一**允许成为「成就第二真源」的部分，
  且每一项都必须能说明「为什么不能重算」。
- **成就解锁记录（全局持久化）**：成就标识 + 难度 + 该难度最早完成年月 + 来源存档 UUID。
- **出身达成记录（全局持久化）**：出身 + 达成类别（绝嗣 / 百年世家）+ 游戏年月 + 来源 UUID。
- **编年史快照（随档持久化）**：存续年数、传承代数、峰值资产、最高功名、进士总数、平均寿命、
  族谱数据面（全量成员，含归档）。
- **结束状态（随档持久化）**：是否已结束 + 结局年月 + 编年史快照。
  三者关系：结束状态**持有**编年史快照，且一旦成立即冻结。
- **待落盘队列（随档持久化）**：未成功写入全局文件的解锁（含原解锁年月），供重试。

  编年史与族谱的**绘制**（U2）、调试控制台 GUI 与 `Suntion` 唤醒路径（U4）、设置面板（U5）。

- **SC-007**：全局文件所在目录不可写时，一回合的结算、存档与备份**照常完成**，且待落盘队列

## Assumptions

> 下列口径是 §17 处理顺序中的「② 采用对玩家最直观的解释」，逐条在实现前登记为 §17 裁决块
> （2026-10-18）。**Q1~Q3 已经用户裁决并采纳本表的推荐解（见 Clarifications，选项 A）；
> 次级口径 5~7 与 12 亦经用户复核已定稿（见下文明细与第 25 条）。**
> 本表**已无未获复核的条目**；若实现阶段发现新空白，按 §17③ 暂停提问并新增裁决块，
> MUST NOT 自造数值（规格书 §17 末句）。

1. **判定时点**（= Q2 裁决 A）：① 每回合**结算完成后**判定一次（消费当月报告 + 状态面）；
   ② **动作型事实**在动作成功后立即判定一次（FR-009 的入口清单）；
   ③ 判定不消费随机、不读钟、不读文件（FR-012）。
2. **解锁不可撤销**（= Q2 裁决 A）：全局记录只增不减；读档/回退不撤销已解锁项。
3. **累计量与编年史随档持久化**（= Q3 裁决 A）：`SaveFileFormat.Version` 自增（007 为 4 → 5），
   旧档按既有版本闸门拒绝读入，不做就地迁移。
4. **全局文件落点**（= Q3 裁决 A 的配套默认）：`achievements.json` 位于 `ISaveService.RootDirectory`，
   格式恒为 JSON，写失败不阻断回合（FR-024）。
5. **存续年数** = 当前年 − 1；**门槛按规格书逐字分档（2026-10-18 复核）**：
   `百年世家` 取 **> 100**（首次成立 = 存续 101 年，即当前年 102）、`千秋万代` 取 **> 300**
   （当前年 302）、`绝处逢生` 取 **≥ 100**（§14.1:570 写「连续存活 100 年」，无「超过」字样）。
6. **传承代数** = 族谱中出现过的**最大 `Person.Generation` + 1**（= 第 N 代的人类读法；
   辈分为 0 基准，见规格书 §4.4:115 与 `src/KFL.Core/Entities/Family.cs:138` 的
   「开局成员的辈分 MUST 为 0」）。故 `五世其昌` = 最大 `Generation >= 4`、
   `三代同堂` = 存在三代（Generation 0/1/2）同时在册。
   「家主更替次数」口径**未被采用**（2026-10-18 复核）。
7. **平均寿命** = 已故成员**享年分布的三均值**（Tukey trimean），`TM = (Q1 + 2·Q2 + Q3) / 4`，
   `decimal` 运算、**保留 3 位小数**（2026-10-18 复核：用户指定三均值与 3 位小数）。
   - **享年定义** = 死亡当月的 `Person.AgeAt`（整岁），**含**夭折、连坐处死、饥馑/患病死亡
     与外嫁归档成员。「天命寿数（`Person.Lifespan`）均值」与「排除稚龄死者」两个口径均未被采用。
   - **分位点算法 = Tukey hinges**（用户裁决 A）：中位把样本分两半、各半再取中位；
     **奇数个样本时中位计入两半**（= R `fivenum` 口径，也与 Tukey 原始 hinges 的深度定义一致）；
     偶数个样本时对半平分。**MUST NOT** 用线性插值（`(n−1)p` / `(n+1)p`）。
   - **小数位**：内部 `decimal` 不截断，快照值 `MidpointRounding.AwayFromZero` 保留 **3 位**。
   - **样本不足也照算**（用户裁决 A，不设特例分支）：n = 1 ⇒ Q1 = Q2 = Q3 = 该值；
     n = 2 ⇒ Q1 = 较小者、Q3 = 较大者；n = 3 ⇒ 中位计入两半（如 `[10, 50, 90]` ⇒ Q1 = 30、Q3 = 70）；
     `n = 0` 取 **0** 且 MUST NOT 抛异常（结局快照必然 n ≥ 1——绝嗣 ⇒ 至少 1 人死亡）。
   - **金色算例（测试 MUST 逐条钉死）**：

     | 享年序列 | Q1 | Q2 | Q3 | 三均值 TM |
     | --- | --- | --- | --- | --- |
     | `[50]` | 50 | 50 | 50 | **50.000** |
     | `[40, 60]` | 40 | 50 | 60 | **50.000** |
     | `[10, 50, 90]` | 30 | 50 | 70 | **50.000** |
     | `[10, 40, 60, 70]` | 25 | 50 | 65 | **47.500** |
     | `[10, 20, 50, 60, 70]` | 20 | 50 | 60 | **45.000** |
     | `[10, 20, 30, 40, 100]`（与「弃中位」口径的判别例） | 20 | 30 | 40 | **30.000** |
     | `[]`（无死亡） | — | — | — | **0.000** |
     | `[1..9]` 均匀 1~9 | 3 | 5 | 7 | **5.000** |

     注：第 6 行是**判别例**——若误用「奇数样本弃中位」的排他口径，该行会得到 Q1 = 15、Q3 = 70、
     TM = 36.250，与上表不符，故该行 MUST 出现在测试里。
8. **进士总数**按**人**计（同一人多次功名变迁只计 1）；最高功名同样按人取历史最高。
9. **峰值资产**只在**月末**采样（每次判定都刷新极大值），口径与 §14.1 的「总资产」一致
   （现金 + 储蓄 + 田宅铺市值 − 贷款）。
10. **「累计举人/进士」按人计**（同一成员的功名记录去重）；「累计落榜」按**家族合计**记
    （解试 + 省试次数之和）。
11. **「名落孙山」取判定时成员的 `Study`**（报告未携带当时的学业值）；若实测发现同月学业可能
    已变化，可在后续版本把学业值加进考生结果行（属形状变更，需回写）。
