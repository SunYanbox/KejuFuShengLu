# Feature Specification: 解决方案骨架与家族领域模型

**Feature Branch**: `001-core-skeleton`

**Created**: 2026-10-05

**Status**: Pending

**Input**: User description: "按《科举浮生录规格书》第 16 节阶段① 起草 001：slnx 解决方案 + Core 实体"

## User Scenarios & Testing *(mandatory)*

后续十二个阶段（月结算、科举、贿赂、官职、婚育、疾病、统计、成就）全部只读写同一份
家族档案。本规格交付的就是这份档案，以及承载它的可构建、可验证、且被自动化守卫的
解决方案骨架。

### User Story 1 - 每一位家族成员都有完整且可校验的档案 (Priority: P1)

玩家的整个游戏过程，本质是在一份家族档案上反复推演。因此每一名成员都必须有一份
完整、无歧义、可校验的档案：身份（姓名、性别、辈分、年龄）、四项天赋、学业、体质、
天命寿数、功名、官阶、政绩、状态、婚姻关系、父母与子女引用、职业指派。任何后续
推演只读写这份档案，不得另立数据副本。

**Why this priority**: 这是规格书 §4.1 的字段全集，也是后续所有公式的共同地基。
字段定义一旦漂移，规则层每一个数值都会跟着错，而错误在越晚的阶段越难回溯。

**Independent Test**: 用一组夹具构造成员与家族（覆盖多代同堂、有配偶、有子女、
处于服刑/外嫁/待阙/已亡状态），逐个断言字段可读可写、取值范围与枚举合法、亲属引用
双向一致且可遍历。全程不需要界面、文件系统或网络。

**Acceptance Scenarios**:

1. **Given** 一个刚建立的空家族，**When** 加入一名开局成员，**Then** 该成员的性别、
   辈分、四项天赋、学业、体质、天命寿数、功名、官阶、政绩、状态、职业指派均可读取，
   且四项天赋与学业落在 0~100、体质落在 0~100。
2. **Given** 一名成员拥有配偶与子女，**When** 查询亲属关系，**Then** 配偶引用双向一致、
   子女的父亲与母亲指向正确，且能沿父系主轴从任一成员向上遍历到祖辈、向下遍历到孙辈。
3. **Given** 一名成员同时处于服刑与禁考，**When** 读取其状态，**Then** 两个状态标记
   同时为真，且互不覆盖（依据规格书 §7.5：禁考与服刑独立并行计时）。
4. **Given** 一名已出嫁的女儿被归档到「外嫁」，**When** 读取家族档案，**Then** 她的
   档案仍然存在且可被读取，不因外嫁而删除（依据规格书 §7.4、§12.1）。

### User Story 2 - 一条命令即可验证构建、测试与解耦 (Priority: P2)

任何人拿到仓库后，都能用一条命令构建整个解决方案并运行全部自动化测试。构建必须
零警告零错误；一旦有人把界面平台类型引入非 UI 层、或让下层反向依赖上层，验证必须
立刻失败而不是等到某次运行出错。

**Why this priority**: 章程把「构建零警告零错误、测试全绿、单一解决方案文件且无旧式
文件共存」定为每个阶段的验收门禁。分层解耦只有被自动化守卫，才不是一句口号。

**Independent Test**: 在干净工作区执行构建与全部测试，断言规格书 §2 的全部工程均
参与其中、不存在旧式解决方案文件；随后以**合成违规输入**注入守卫的判定逻辑（反向依赖、
界面平台类型泄漏各一），断言守卫失败并指出违规工程或依赖边。合成输入是**唯一可执行**的
验证路径：真实改写仓库来制造这两类违规会**同时破坏构建**（本方案的允许边集是全序，
任何反向边都闭合成环，见 quickstart §2），此时「守卫失败」与「编译失败」无法区分。

**Acceptance Scenarios**:

1. **Given** 一份干净的工作区，**When** 执行解决方案构建，**Then** 以零警告零错误结束，
   且解决方案由单一 XML 解决方案文件描述、不存在旧式解决方案文件。
2. **Given** 已完成构建的解决方案，**When** 运行全部自动化测试，**Then** 全部通过。
3. **Given** 有人把界面平台类型引入非 UI 层工程，**When** 运行守卫测试，**Then** 守卫
   失败并指出违规工程。
4. **Given** 有人让下层工程反向依赖上层工程，**When** 运行守卫测试，**Then** 守卫失败
   并指出违规的依赖边。

### User Story 3 - 时间与随机性可注入，建模结果可复现 (Priority: P3)

所有与随机性有关的建模行为，都通过可注入的随机来源获得，而不是直接读全局随机数；
与时间有关的建模行为，读的是可注入的**游戏时间来源**（推演出的年月），而不是系统
时钟。给定相同输入，建模结果可完全复现。

**Why this priority**: 章程第 IV 条要求确定性可复现，这是后续所有随机结算能被单测
覆盖的前提；同时它是第 II 条「跨层协作通过下层接口完成」的具体落点。本阶段只引入
随机来源与游戏时间来源两组抽象，其余跨层接口留到各自阶段。

**Independent Test**: 以固定种子的随机来源与固定的游戏时间来源创建同一存档级状态
（本阶段的建模过程：生成唯一标识、确定起始年月），断言两次结果完全一致；并以静态
检查断言非 UI 层不存在对系统时钟、全局随机、文件系统与网络的直接访问。

**Acceptance Scenarios**:

1. **Given** 注入了固定种子的随机来源与固定的游戏时间来源，**When** 两次创建同一
   存档级状态，**Then** 两次得到的唯一标识与起始年月完全一致。
2. **Given** 非 UI 层工程，**When** 执行静态检查，**Then** 不存在对系统时钟、全局随机、
   文件系统与网络的直接访问。

### Edge Cases

- 成员在同一月份内既处于服刑、又被禁考，且天命寿数到期：状态并存与「已亡」归档
  必须同时成立，不得因其中一个状态而丢失另一个（规格书 §7.5、§4.1）。
- 婚姻一方死亡后存活方再婚（规格书 §9.1）：档案必须能表达当前配偶与既往婚姻，
  不得因再婚而让子女的父母引用断裂。
- 开局「士」出身的家主是举人，但开局士出身不计入「仕」身份（规格书 §10.2）：
  档案必须把「出身」与「仕身份」表达为两个独立属性，二者可并存。
- 死亡成员必须归档而不是删除，族谱与统计仍可读取其数据（规格书 §12.1、§15）。
- 成员同时承担多个亲属角色时（例如某成员既是某人的配偶，又是另一成员的父/母），
  亲属引用不得产生重复节点或指向自身的闭环。
- 一名进士因地狱殿试连坐被降为贡士（规格书 §7.4）：功名变迁历史 MUST 追加一条降级记录，
  当前功名 MUST 随之下降，MUST NOT 出现「历史末条是进士、实际功名是贡士」的矛盾。
- 买来的旁系成员终身未与家族内成员成婚（规格书 §9.5 与 §4.4）：其辈分取购买时确定的
  「家主辈分 + 1」，MUST NOT 因无配偶而无法在家族树中定位。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以规格书 §2 列出的六项工程（`KFL.Core`、`KFL.Infrastructure`、
  `KFL.Rules`、`KFL.Presentation`、`KFL.App`、`KFL.Tests`）组成单一解决方案，且
  MUST NOT 同时存在旧式解决方案文件（规格书 §1、§2；章程「技术栈与工程约束」）。
- **FR-002**: 非 UI 层工程 MUST 以 `net10.0` 为目标框架，UI 层工程 MUST 以
  `net10.0-windows` 为目标框架；SDK 版本 MUST 由仓库根的配置文件固定，保证本机与
  CI 使用同一基线（规格书 §1；章程原则 I）。
- **FR-003**: 依赖方向 MUST 严格单向：`KFL.Core` ← `KFL.Infrastructure` ← `KFL.Rules`
  ← `KFL.Presentation` / `KFL.App`；非 UI 层 MUST NOT 引用界面平台专属类型
  （规格书 §2；章程原则 II）。
- **FR-004**: 领域档案 MUST 覆盖规格书 §4.1 的全部字段：姓名、年龄、性别、辈分、
  四项天赋、学业、体质、天命寿数、功名、官阶、政绩、状态、婚姻关系、父母与子女引用、
  职业指派。
- **FR-005**: 四项天赋（农、商、仕、工）MUST 表达为出生即定、且不因游戏行为升降的
  属性，取值范围为 0~100（规格书 §4.1）。
- **FR-006**: 学业与体质 MUST 表达为可变的 0~100 属性，且 MUST NOT 与天赋共用同一
  字段或同一可变通道（规格书 §4.1）。
- **FR-007**: 天命寿数 MUST 在成员出生时确定、终身不再改变，并 MUST 可被读取以便
  在卡片上对玩家展示（规格书 §4.1、§12.2）。
- **FR-008**: 功名 MUST 以**按时间顺序的变迁历史**表达规格书 §6 的完整链条
  （白身 → 举人 → 贡士 → 进士），每次变化 MUST 记录年月与变化原因（开局带入 / 科举中式 /
  §7.4 连坐降级 / 调试改写），且进士 MUST 能额外表达一甲名次（状元 / 榜眼 / 探花）；
  当前功名 MUST 由末条记录派生，MUST NOT 另存可能与之失配的独立字段
  （规格书 §4.1、§6、§7.4、§12.2）。
- **FR-009**: 官阶 MUST 表达规格书 §8 的十八级；成员 MUST 能表达「当前无官职」与
  「任职于 L1~L18 之一」两种情形（规格书 §8）。
- **FR-010**: 状态 MUST 覆盖规格书 §4.1 的九种标记（患病、饥馑、服刑、待阙、禁考、
  禁升、外嫁、致仕、已亡），并 MUST 允许同时成立（规格书 §7.5）。
- **FR-011**: 家族 MUST 记录成员之间的血缘与婚姻关系，使任一成员可沿父系主轴向上与
  向下遍历，并定位其配偶；婚姻为**一夫一妻**（任一成员至多一个当前配偶，已有配偶者
  MUST NOT 被指定第二个），丧偶后可再婚（先清空当前配偶、把前任移入既往配偶）。家族
  MUST 承载**辈分**（血亲出生即定且终身不变；外来者按规格书 §4.4 由家族指定、且 MUST
  在其尚无子女时落定；**开局成员为 0**，即规格书 §4.4 的「辈分自创始者为 0」）与
  **家主**（指向在册成员的持久身份）（规格书 §4.1、§4.4、§9.1、§12.1）。
- **FR-012**: 存档级状态 MUST 记录当前游戏年月、当前难度与唯一标识（UUID，以 `Guid`
  表示），且该标识 MUST NOT 随存档改名而变化（规格书 §3、§11、§14）。**后一子句在 001
  内无可验证对象**——档名与存档落盘属阶段④，本阶段只校验「标识非空」与「标识无公开
  写入通道」两件事；改档名不变性的验证随阶段④ 落盘时引入（见 FR-005 同类的「无写入
  通道」口径）。
- **FR-013**: 随机性与游戏时间 MUST 通过可注入的来源提供（随机来源、游戏时间来源两组
  抽象）；非 UI 层 MUST NOT 直接访问系统时钟、全局随机数、文件系统或网络
  （章程原则 II、原则 IV）。
- **FR-014**: 系统 MUST 提供自动化架构守卫，使反向依赖或界面平台类型泄漏导致验证
  失败，而不是仅靠人工评审（章程原则 II、开发工作流与质量门禁）。
- **FR-015**: 领域与规则测试 MUST 能在无界面、无文件系统、无网络依赖的条件下运行
  （章程原则 IV）；架构守卫测试 MAY 读取本仓库的工程文件与源码，这不构成运行时依赖。

### Key Entities

- **成员档案（Person）**：家族的一位成员。关键属性为身份（姓名、性别、辈分、出生年月）、
  四项天赋、学业、体质、天命寿数、**功名变迁历史**（按时间顺序记录每一次变化：年月、功名、
  一甲名次、变化原因；当前功名由末条派生）、官阶、政绩、状态标记集合、职业指派，以及
  指向父母与配偶（含既往配偶）的亲属引用。天赋不可变，学业与体质可变，天命寿数出生即定，
  年龄由出生年月派生；辈分对血亲成员出生即定且终身不变，对外来者（娶入配偶、买来的旁系）
  由家族按规格书 §4.4 指定。
- **家族（Family）**：成员的集合与家族标识（姓氏），承载血缘主轴与婚姻关系，并区分
  「在册」（未亡且未外嫁）与「已归档」（已亡、外嫁）两类成员；成员及其配偶的子女
  引用由家族按索引派生，避免双向冗余失配。家族还记录「仕身份」（规格书 §10.2）、
  **家主**（规格书 §4.4 的持久身份，指向在册成员）以及外来者辈分的指定。
- **存档状态（GameState）**：一次推演的顶层状态。关键属性为唯一标识（UUID，以 `Guid`
  表示）、
  当前游戏年月、当前难度、出身（农/工/商/士，规格书 §10.1）、当前家族，以及后续
  阶段将追加的资产与统计容器。
- **功名（Degree）**：白身、举人、贡士、进士四级；进士附一甲名次（状元/榜眼/探花）。
- **官阶（Rank）**：规格书 §8 的 L1~L18，或无官职。
- **出身（Origin）**：农、工、商、士四类终身特性来源；与「仕身份」（进士直系血统）
  是两个彼此独立、可并存的属性。
- **状态标记（StatusFlag）**：患病、饥馑、服刑、待阙、禁考、禁升、外嫁、致仕、已亡，
  可并存，并携带各自的计时信息（如服刑剩余月数）。

## Out of Scope

- 任何月度结算与数值计算（规格书 §16 阶段②及以后）：生活费、收入、贷款、储蓄、
  饥馑四阶段流转。
- 资产（田、农村宅、城市宅、铺面）与现金/储蓄/贷款池的建模（规格书 §5.3、§5.4；
  阶段②）。规格书 §2 对 `KFL.Core` 的实体清单不含资产，故本阶段不建。
- 买人口的购买入口与递增计价结算（规格书 §9.5，阶段②经济）：本阶段只保证档案能表达
  「无父母参照的旁系成员」以及按 §4.4 指定的辈分，不实现购买流程与价格。
- 按角色与家族级的每月收支流水账及其统计聚合（规格书 §12.3；阶段②产生条目、阶段⑩
  消费）：本阶段只把账本形状定下（见 research R-16），不建任何账本字段。
- 家主继任判定（规格书 §4.4；依赖阶段⑧的死亡推进）：本阶段只承载家主属性与其不变量。
- 主界面、卡片墙、家族树、筛选器与统计页（阶段③、⑨、⑩）。
- 存档的落盘读写、备份与成就持久化（阶段④、⑪）；本阶段只定义字段，不做持久化。
- 科举周期、贿赂与惩罚矩阵、连坐、服刑与禁考计时推进（阶段⑤、⑥）。
- 调试控制台（阶段⑦）。
- 官职晋升、婚育、疾病与寿命的推进逻辑（阶段⑧）。
- 四项出身开局的交互流程与初始资产发放（规格书 §10.1）：其数值落地属阶段③，
  本阶段只保证档案能表达「出身」这一属性。
- 存档、成就与事件总线三组跨层接口的具体定义：各自阶段引入，本阶段只引入时间与
  随机来源两组抽象。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 规格书 §2 列出的六项工程全部纳入单一解决方案文件，一条命令即可完成
  构建，且构建结果为零警告零错误。（判定对象与边界见 FR-001、FR-002，本节不另立口径。）
- **SC-002**: 领域与规则测试在无界面、无文件系统、无网络依赖的环境中全绿；架构守卫
  测试仅额外读取本仓库的工程文件与源码。（扫描范围与豁免见 FR-015、FR-014 及契约一
  G-07，本节不另立口径。）
- **SC-003**: 故意引入的反向依赖与界面平台类型泄漏**以合成违规输入注入**，被守卫测试
  100% 捕获（两种违规各验证一次），且失败信息能指出违规工程或依赖边（见 FR-014）。
- **SC-004**: 非 UI 层对系统时钟、全局随机数、文件系统与网络的直接访问出现 0 次。
- **SC-005**: 规格书 §4.1 列举的成员字段与九种状态在档案中 100% 有对应表示，无遗漏。
- **SC-006**: 从任一成员出发，均可在一次查询内定位其父母、配偶与子女；不存在单向
  引用或断裂引用（以多代同堂夹具断言，覆盖 3 代以上）。

## Assumptions

- 规格书是唯一的需求与数值真源。本规格未自创任何数值，全部字段与约束均标注了
  对应的规格书章节号（章程「需求真源」）。
- 本规格严格对应规格书 §16 阶段①（slnx 解决方案 + Core 实体），未跨阶段提前实现
  后续能力；如后续需要合并阶段，应在计划文档中说明理由。
- 规格书 §16「必测单测清单」中属于本阶段的仅为实体不变量、亲属引用一致性与解耦
